1. Toolchain Setup

To build Zirvium you need a freestanding x86-64 C compiler and a few supporting tools:

The Makefile automatically falls back from x86_64-elf-gcc to the system gcc if the cross-compiler is not found.

Quick start:

git clone https://github.com/gauthamnair2005/zirvium.git
cd zirvium
git submodule update --init --recursive

The kernel is compiled with -std=c11 -ffreestanding -mno-sse -mno-sse2 -mno-red-zone -mcmodel=kernel -O2 and linked with -nostdlib -T kernel/kernel.ld.

4. Boot Process

The boot sequence proceeds in two phases: an assembly stub that transitions to long mode, followed by the C kernel_main() orchestrator.

Phase 1: Assembly Stub (arch/x64/boot.asm)

  1. GRUB2 loads the kernel via Multiboot2 protocol (entry at _start)
  2. 32-bit stub checks CPUID and long mode support
  3. Builds identity-mapped page tables covering 4 GiB via 2 MiB huge pages
  4. Creates higher-half kernel map at 0xFFFFFFFF80000000
  5. Loads 64-bit GDT and far-jumps into long mode

Phase 2: kernel_main() — 20-Step Init

5. Physical Memory Manager

Location: kernel/mm/pmm.c

The PMM uses a bitmap allocator with one bit per 4 KiB physical frame. It supports up to 1 TiB of physical memory (256M entries × 4 KiB = 1 TiB). The bitmap is placed in the lowest available physical region after the kernel and is parsed from the Multiboot2 memory map.

FunctionDescription
pmm_init(mmap, mmap_count)Parse MB2 memory map, build bitmap of free frames
pmm_alloc()Allocate a single 4 KiB frame (returns physical address)
pmm_alloc_multi(count)Allocate contiguous frames
pmm_free(addr)Free a single frame
pmm_free_multi(addr, count)Free contiguous frames

Allocation is O(n) linear scan of the bitmap.

7. Kernel Heap

Location: kernel/mm/heap.c

The kernel heap is a simple bump allocator over a 4 MiB arena. Used for temporary allocations during boot and driver initialization.

FunctionDescription
kmalloc(size)Allocate from heap arena (returns virtual address)
kfree(ptr)Free (no-op; arena is reset on reboot)

8. Process Management

Location: kernel/proc/process.c

Process management covers creation, scheduling, memory management, and the kernel's execve save/restore mechanism.

struct process {
    uint64_t pid;
    struct context ctx;       // Saved registers (RSP, RIP, RBP, RBX, R12-R15)
    pml4_t *pml4;             // Address space (CR3 value)
    struct file *files[16];   // File descriptor table (16 FDs)
    uint64_t heap_brk;        // Program break for brk/sbrk
    uint64_t stack_phys;      // Physical address of user stack
    int status;               // Running, zombie, blocked, etc.
    uint64_t wake_time;       // For timed waits
};

execve Save/Restore

The kernel implements a unique execve mechanism: instead of fork+exec, the caller's address space is saved before loading the new binary, and restored when the child exits. This allows the shell to run external commands and return to the prompt without needing fork().

  1. Save caller's page tables, stack pointer, and heap break
  2. Load new ELF binary into a fresh address space
  3. Switch to new process and enter user mode
  4. On exit, restore the saved context and resume the caller

Location: fs/

12. IPC

Location: kernel/ipc/pipe.c, kernel/ipc/mqueue.c

Two IPC primitives: ring-buffer pipes (unidirectional, FD-based) and message queues (256 slots × 64 bytes, integer ID). The scheduler supports a BLOCKED process state — blocked processes are skipped until woken by mq_wake_waiters when data arrives.

HPC/MPI primitives (kernel/hpc/hpc.c) provide distributed-computing operations on top of message queues: auto-assigned ranks, barrier synchronisation, tagged send/recv, broadcast, and reduction (SUM/MAX/MIN).

14. Driver Framework

Location: drivers/

The Zirvium driver framework uses a simple registration/probe model. Drivers register themselves with the kernel; PCI enumeration triggers probing based on vendor/device IDs. The linux_compat.h header (610 lines) allows Linux kernel source to compile under MOSIX with minimal changes.

Ported drivers: Enveediya GPU (RTX/B-series), Intel Arc GPU (A/B/C-series), AMD Radeon GPU (GCN/RDNA 1–3.5), VirtIO block/net, RTL8139 NIC, xHCI USB 3.0/2.0, Thunderbolt 3/4 & USB4, WiFi 7 802.11be (Intel BE200, MediaTek MT7927, Qualcomm QCNCM865, Broadcom BCM4389).

15. ELF Loader

Location: kernel/loader/elf.c

Loads static no-pie ELF64 binaries. Processes PT_LOAD segments with correct non-page-aligned handling (page_off = vaddr & 0xFFF). Does not support shared libraries or PIE. All userspace binaries are statically linked and embedded via incbin in kernel/loader/init_bin.asm.

16. Console

Location: kernel/console.c

Triple-output console: serial (COM1), VGA text mode, and pixel framebuffer. Exposed to userspace as /zirv/tty/virtual0 (read = keyboard, write = display).

17. zirvlibc Internals

Location: libs/zirvlibc/

Freestanding C library. Syscall wrappers via inline assembly (_syscall0 through _syscall6). Provides string.h, stdio.h (printf), stdlib.h, ctype.h, unistd.h, datetime.h, dirent.h.

18. zirvinit

Location: zirvinit/ (submodule)

PID 1. 28 lines of C: prints banner, calls execve to start the shell.

19. zirvshell

Location: zirvshell/ (submodule)

Reference MOSIX shell with English-like syntax. 20 built-in commands. Uses execve save/restore to run external commands without forking.

20. Porting Guide

Porting to a new architecture

  1. Create arch/<arch>/ with boot code, context switch, interrupt dispatch, MMU, timer
  2. Implement cpu.h, gdt.h, idt.h
  3. Update Makefile and linker script

Building a MOSIX-compliant kernel from scratch

  1. Implement the MOSIX syscall ABI
  2. Create the MOSIX filesystem hierarchy
  3. Implement /zirv device namespace
  4. Add console device at /zirv/tty/virtual0
  5. Implement ELF64 loading
  6. Link against zirvlibc

23. Audio Subsystem

Location: kernel/audio/ (core), drivers/zirv/audio/ (drivers)

PCM audio with Intel HDA and AC97 drivers. Syscalls: 126 (AUDIO_PLAY, 16-bit stereo 48 kHz), 127 (AUDIO_VOLUME, 0–255). Nokia composer tool in zirvutils generates square-wave ringtone-style music.

24. ZirvFlux Library

ZirvFlux is the reference MOSIX display framework. Provides a Mesa-like C API (zf_connect, zf_create_buffer, zf_write_buffer, zf_present) abstracting the DisplayJet kernel driver. All data encrypted at rest via ChaCha20.

25. DisplayJet API

11 syscalls (110–120) for compositor protocol. Drives Bochs VBE at 1024x768x32bpp. Full MAEM encryption. See the DisplayJet page.

26. ZirvTK GUI Toolkit

ZirvTK is a Rust GUI toolkit with C FFI providing a complete desktop compositor for MOSIX. Written in no_std Rust with a custom arena allocator. Key features:

  • Desktop compositor: Full render loop with taskbar, app launcher, clock, particles, glass panels
  • Scanline-optimised rendering: fill_round_rect/stroke_round_rect use O(h) scanline spans instead of O(w×h) per-pixel hit-testing
  • Anti-aliased text: Bilinear-interpolated scaled bitmap font
  • SVG vector path icons: Compact MoveTo/LineTo path definitions with anti-aliased polygon fill
  • Particle system: 80 ambient particles with per-particle colour cycling
  • Animated hover: Sinusoidal glow pulse on launcher icons
  • VBE page flipping: Tear-free display via Y_OFFSET flip
  • Widget set: AppLauncher, TaskBar, FuturisticClock, GlassPanel, NeonButton, GlowSlider, AnimatedToggle
  • C FFI: ztk_desktop_run(), ztk_fb_* raw framebuffer functions, ztk_draw_icon_path

Build: ZIRVFLUX_DIR=../zirvflux cargo build --release --no-default-features --features alloc

27. ZirvUI Compositor

Thin C stub that initialises ZirvFlux and calls ztk_desktop_run() to enter the ZirvTK desktop compositor loop. All rendering, widgets, and input handling are delegated to ZirvTK. This means UI updates only require toolkit changes — ZirvUI itself is unchanged.

Full documentation on the ZirvUI page.

29. ZirvFS — Native CoW+Git Filesystem

Location: fs/zirvfs.h, fs/zirvfs.c, fs/zirvfs_block.c, fs/zirvfs_snap.c, fs/sha256.c

ZirvFS is a native Copy-on-Write, content-addressed filesystem inspired by Git. It is the default filesystem for all block storage devices (SATA, NVMe, USB, VirtIO) in Zirvium. Every device is automatically formatted and mounted at boot under /mounts/zirvfs<N>.

Architecture

ZirvFS uses SHA-256 content hashing for all objects. There are three object types:

  • BLOB — raw file data, identified by its SHA-256 hash
  • TREE — directory entries mapping names to hashes (sorted for binary search)
  • COMMIT — snapshot metadata: timestamp, author, message, parent hash, tree hash

The superblock at block 0 stores the root tree hash, root commit hash, block size, free block bitmap location, and volume label (magic "ZIRVFS00").

Adaptive Block Size

Media ClassBlock SizeStorage Types
DEV_CLASS_PENDRIVE4 KiBUSB flash drives, SD cards
DEV_CLASS_SSD16 KiBSATA/NVMe SSDs, flash storage
DEV_CLASS_HDD64 KiBMechanical hard drives, large block devices

Block size is auto-detected at mount time from dev_class_t via zirvfs_detect_block_size().

Copy-on-Write

Every write allocates new blocks from the bitmap allocator (zirvfs_alloc_block). The old blocks remain referenced by their hash and can be restored via snapshot rollback. Metadata updates are atomic — the superblock root pointers are only updated after a successful commit.

Multi-block objects chain via a 64-bit next-block pointer stored in the last 8 bytes of each block (big-endian for SHA-256 compatibility).

Snapshots (Git-like)

FunctionDescription
zirvfs_snapshot_create(fs, message, &snap_id)Create a commit of the current root tree with a message
zirvfs_snapshot_list(fs, snaps, &count)List all snapshots (id, timestamp, message)
zirvfs_snapshot_restore(fs, snap_id)Restore root tree to a previous snapshot state

Syscall wrappers (152–154) expose snapshots to userspace. Shell commands snapcreate, snaplist, snaprestore and the /bin/snapshot utility provide interactive access.

VFS Integration

ZirvFS implements the MOSIX vnode_ops_t interface:

OperationImplementation
read(vnode, buf, count, offset)Reads file data from BLOB object, seeks at tree_entry offset
readdir(vnode, idx, name, namelen)Lists directory entries from TREE object
lookup(dir, name)Lookup name in TREE, return child vnode
create(dir, name, mode)Insert new TREE entry (writable)
unlink(dir, name)Remove TREE entry

The private_data pointer on each vnode stores the zirvfs_t instance for the filesystem. The root vnode is created in zirvfs_mount() and inserted into the VFS tree at /mounts/zirvfs<N>.

Boot Initialisation

Called from kernel_main() step 6g, after tmpfs is mounted:

static void zirvfs_init(void)
{
    for each registered storage device:
        if device has working read_sectors/write_sectors:
            create zirvfs_t instance
            detect block size from dev_class_t
            try to mount existing ZirvFS volume
            if no valid superblock: format device
            create root vnode, insert into VFS tree
            log success ("ZirvFS volume N mounted")
}

Each volume is accessible at /mounts/zirvfs0, /mounts/zirvfs1, etc.
