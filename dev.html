1. Toolchain Setup

To build Zirvium you need a freestanding x86-64 C compiler and a few supporting tools:

ToolPurposeInstall (Ubuntu/Debian)

nasm >= 2.14x86-64 assemblersudo apt install nasm
grub-mkrescueGRUB2 bootable ISO creationsudo apt install grub-pc-bin grub-common xorriso
mtoolsDOS filesystem tools for ISO buildsudo apt install mtools

The Makefile automatically falls back from x86_64-elf-gcc to the system gcc if the cross-compiler is not found.

Quick start:

git clone https://github.com/gauthamnair2005/zirvium.git
cd zirvium
git submodule update --init --recursive

The kernel is compiled with -std=c11 -ffreestanding -mno-sse -mno-sse2 -mno-red-zone -mcmodel=kernel -O2 and linked with -nostdlib -T kernel/kernel.ld.

4. Boot Process

The boot sequence proceeds in two phases: an assembly stub that transitions to long mode, followed by the C kernel_main() orchestrator.

Phase 1: Assembly Stub (arch/x64/boot.asm)

  1. GRUB2 loads the kernel via Multiboot2 protocol (entry at _start)
  2. 32-bit stub checks CPUID and long mode support
  3. Builds identity-mapped page tables covering 4 GiB via 2 MiB huge pages
  4. Creates higher-half kernel map at 0xFFFFFFFF80000000
  5. Loads 64-bit GDT and far-jumps into long mode

Phase 2: kernel_main() — 20-Step Init

5. Physical Memory Manager

Location: kernel/mm/pmm.c

The PMM uses a bitmap allocator with one bit per 4 KiB physical frame. It supports up to 1 TiB of physical memory (256M entries × 4 KiB = 1 TiB). The bitmap is placed in the lowest available physical region after the kernel and is parsed from the Multiboot2 memory map.

FunctionDescription
pmm_init(mmap, mmap_count)Parse MB2 memory map, build bitmap of free frames
pmm_alloc()Allocate a single 4 KiB frame (returns physical address)
pmm_alloc_multi(count)Allocate contiguous frames
pmm_free(addr)Free a single frame
pmm_free_multi(addr, count)Free contiguous frames

Allocation is O(n) linear scan of the bitmap. Frames are marked as used or free by setting the corresponding bit.

6. Virtual Memory Manager

Location: kernel/mm/vmm.c

The VMM implements 4-level paging (PML4 → PDPT → PD → PT). Each process has its own address space; the kernel upper half is cloned from the master kernel page tables.

7. Kernel Heap

Location: kernel/mm/heap.c

The kernel heap is a simple bump allocator over a 4 MiB arena. It is used for temporary kernel allocations during boot and driver initialization.

FunctionDescription
kmalloc(size)Allocate from heap arena (returns virtual address)
kfree(ptr)Free (no-op; arena is reset on reboot)

The heap is not designed for sustained use — long-lived allocations use the PMM/VMM directly. A full slab allocator is planned for future releases.

8. Process Management

Location: kernel/proc/process.c

Process management covers creation, scheduling, memory management, and the kernel's execve save/restore mechanism.

Key Structures

struct process {
    uint64_t pid;
    struct context ctx;       // Saved registers (RSP, RIP, RBP, RBX, R12-R15)
    pml4_t *pml4;             // Address space (CR3 value)
    struct file *files[16];   // File descriptor table (16 FDs)
    uint64_t heap_brk;        // Program break for brk/sbrk
    uint64_t stack_phys;      // Physical address of user stack
    int status;               // Running, zombie, etc.
    uint64_t wake_time;       // For timed waits
};

execve Save/Restore

The kernel implements a unique execve mechanism: instead of fork+exec, the caller's address space is saved before loading the new binary, and restored when the child exits. This allows the shell to run external commands and return to the prompt without needing fork(). The sequence is:

  1. Save caller's page tables, stack pointer, and heap break
  2. Load new ELF binary into a fresh address space
  3. Switch to new process and enter user mode
  4. On exit, restore the saved context and resume the caller

Process Lifecycle

proc_init_stdio(proc)Wire up stdin/stdout/stderr to console
proc_enter_usermode(proc)Switch to ring 3 via IRETQ
proc_exit(status)Mark process as zombie, wake parent
wait4(pid, &status)Wait for child, reap zombie

10. Time Subsystem

Location: kernel/time/time.c

Timekeeping is provided by two independent sources: CMOS RTC for absolute date/time and the TSC (timestamp counter) for uptime measurement.

12. IPC

Location: kernel/ipc/pipe.c, kernel/ipc/mqueue.c

Two IPC primitives are provided:

Pipes

Ring-buffer pipes created via the SYS_PIPE syscall. Pipes are unidirectional and support read/write with blocking semantics.

FunctionDescription
pipe_create(pipefd)Create a pipe, return read and write FDs
pipe_read(pipe, buf, size)Read from pipe (blocks if empty)
pipe_write(pipe, buf, size)Write to pipe (blocks if full)
pipe_close(pipe)Close pipe endpoint

The pipe buffer is a fixed-size ring buffer allocated in kernel memory. Pipes are identified by file descriptors and follow the standard MOSIX read/write model.

Message Queues

Ring-buffer message queues (kernel/ipc/mqueue.c) with 256 message slots of 64 bytes each. Queues are identified by integer IDs and support multipoint communication (any process with the ID can send/receive).

SyscallFunctionDescription
140mq_create()Allocate a new message queue, return its ID
141mq_send(qid, msg, len)Send a message (returns -1 if full)
142mq_recv(qid, buf, len)Receive a message (blocks caller if empty using PROC_STATE_BLOCKED)
143mq_destroy(qid)Free a message queue

The scheduler supports a BLOCKED process state: blocked processes are skipped in the scheduling loop. When a message arrives, mq_wake_waiters transitions waiting processes back to RUNNING. Message queues serve as the transport layer for the HPC subsystem.

HPC / MPI Primitives

Built on top of message queues, the HPC subsystem (kernel/hpc/hpc.c) provides distributed-computing primitives for multi-process workloads:

SyscallFunctionDescription
144hpc_get_rank()Return this process's auto-assigned rank (0–N−1)
145hpc_get_size()Return the total number of HPC-registered processes
146hpc_barrier()Block until all processes reach this call (shared-MQ synchronisation)
147hpc_send(rank, tag, data, len)Send a tagged message to a specific rank
148hpc_recv(rank, tag, buf, len)Receive a tagged message from a specific rank
149hpc_bcast(root, data, len)Broadcast data from root rank to all others
150hpc_reduce(op, data, len, result)Reduce values across all ranks (SUM, MAX, MIN)

On a single-CPU system, barrier synchronisation is synchronous by nature (only one process runs at a time) but provides correct ordering. All HPC communication uses tagged message queues per rank.

13. Interrupt Handling

Location: kernel/irq/irq.c, arch/x64/idt.c

The interrupt system is built on three layers: IDT entry points in assembly, C exception handlers, and the 8259A PIC for hardware IRQs.

14. Driver Framework

15. ELF Loader

Location: kernel/loader/elf.c

The ELF loader reads ELF64 binaries and maps them into a process address space. It supports static, no-pie executables compiled with -nostdlib -static -no-pie.

FunctionDescription
elf_load(elf_data, size, &entry)Parse ELF64 header, load segments, return entry point
elf_load_process(proc, elf_start)Load ELF into a process address space

The loader processes PT_LOAD segments, allocating pages via the PMM and mapping them into the process's VMM address space. It does not support shared libraries, dynamic linking, or PIE executables. All userspace binaries are statically linked and embedded into the kernel via incbin.

Embedded Binaries

The kernel/loader/init_bin.asm file uses NASM incbin directives to embed all userspace ELFs directly into the kernel image. The embedded.c module provides a table mapping binary names to their in-memory locations and sizes.

16. Console

Location: kernel/console.c

The kernel console provides triple-output logging: serial (COM1), VGA text mode, and pixel framebuffer. The console subsystem initializes early in boot and remains active throughout system operation.

FunctionDescription
console_init()Initialize console subsystem
console_enable_vga()Enable VGA text mode output
kputs(str)Print string to all active consoles
kprintf(fmt, ...)Formatted print (supports %s, %d, %x, %p)

The console device is exposed to userspace as /zirv/tty/virtual0, which provides read (keyboard input) and write (display output) operations. The shell and utilities interact with the system through this device node.

17. zirvlibc Internals

Location: libs/zirvlibc/

zirvlibc is the reference MOSIX C library — a freestanding libc providing all the functions needed by MOSIX userspace programs. It is compiled as a static library (libzirvlibc.a) and linked into every userspace binary.

Syscall Wrappers

All syscalls are wrapped via inline assembly (_syscall0 through _syscall6) that issues the SYSCALL instruction:

static inline uint64_t _syscall1(uint64_t n, uint64_t a1) {
    uint64_t ret;
    asm volatile("syscall" : "=a"(ret) : "a"(n), "D"(a1) : "rcx", "r11", "memory");
    return ret;
}

Library Structure

18. zirvinit

Location: zirvinit/ (submodule)

zirvinit is the first userspace process (PID 1). Its source is deliberately minimal — 28 lines of C:

#include <stdio.h>
#include <unistd.h>

int main(void) {
    puts("MOSIX v0.1 — Zirvium Reference Kernel");
    puts("init: starting shell...");
    execve("/bin/shell", (char *[]){(char *)"/bin/shell", NULL}, NULL);
    for (;;);  // halt if execve fails
}

The kernel creates PID 1, loads zirvinit.elf from the embedded binary table, wires up the console as stdin/stdout/stderr, and enters user mode. zirvinit then execves into the shell, which becomes the primary user interface. If the shell binary is missing, init halts forever.

As PID 1, zirvinit inherits orphaned processes. The kernel reparents children of exiting processes to PID 1, which collects their exit status via the wait4 mechanism.

19. zirvshell

Location: zirvshell/ (submodule)

zirvshell is the reference MOSIX shell. It implements a command-line interface with English-like natural language syntax alongside standard POSIX aliases.

Command Loop

  1. Print prompt ("/ $ " or "/dir $ ")
  2. Read a line from stdin (with backspace line editing)
  3. Parse into command and arguments (supports double-quoted strings)
  4. Match against built-in command list (including natural language aliases)
  5. If found, execute the built-in handler
  6. If not found, attempt execve("/bin/<command>") via the save/restore mechanism
  7. On return, loop back to prompt

Built-in Commands

20 commands: help, echo, pwd, uname, whoami, clear, ls, cat, run, cd, date, settime, timezone, uptime, reboot, shutdown, suspend, mkdir, rm, exit. Many have English aliases: help me please, clear the screen, go to, show files, say.

execve Save/Restore Integration

When the shell runs an external command via execve(), the kernel saves the shell's address space, loads the utility binary, runs it to completion, and restores the shell. This allows external commands to run without the shell needing to fork.

20. Porting Guide

Porting the kernel to a new architecture

  1. Create arch/<arch>/ with boot code, context switch, interrupt dispatch, MMU, timer
  2. Implement cpu.h, gdt.h, idt.h
  3. Update Makefile and linker script

Implementing a MOSIX-compliant kernel from scratch

To build your own kernel that runs MOSIX userspace:

  1. Implement the MOSIX syscall ABI (24 syscalls, numbers 0-101)
  2. Create the MOSIX filesystem hierarchy (/bin, /lib, /user, /boot, /config, /zirv, /mounts, /tmp)
  3. Implement the /zirv device namespace with bus subdirectories
  4. Add at minimum the console device at /zirv/tty/virtual0 (read from keyboard, write to display)
  5. Implement ELF64 binary loading for static no-pie executables
  6. Link against or implement the syscall wrappers from zirvlibc

Adding a syscall

  1. Add SYS_* in both kernel/syscall/syscall.h and libc include/zirv/syscall.h
  2. Implement handler in kernel/syscall/syscall.c
  3. Add dispatch case
  4. Add libc wrapper and prototype

23. ZirvFlux Library

ZirvFlux is the reference MOSIX display framework library. It provides a Mesa-like API for compositors, abstracting the DisplayJet kernel driver behind a clean C interface. Compositors call zf_connect(), zf_create_buffer(), zf_write_buffer(), and zf_present() instead of invoking DisplayJet syscalls directly.

The library handles buffer management (up to 32 GPU surfaces), display enumeration, and region-based presentation. All data written through ZirvFlux is encrypted at rest by the underlying DisplayJet driver using ChaCha20 with per-surface HKDF-SHA256 keys.

Full documentation on the ZirvFlux page.

24. DisplayJet API

11 custom syscalls (110-120) for a compositor-based display protocol. Drives Bochs VBE at 1024x768x32bpp. All surfaces encrypted with ChaCha20 (MAEM). Full documentation on the DisplayJet page.

25. ZirvTK GUI Toolkit

ZirvTK is a Rust GUI toolkit with C FFI for building MOSIX graphical applications. Provides a complete widget tree (Button, Label, Panel, Window, TileScroller, MediaTile), software Canvas renderer with 5x7 bitmap font, and platform abstraction over ZirvFlux.

Written in no_std Rust with a custom arena allocator for freestanding environments. Builds as staticlib, cdylib, and rlib. The C FFI layer (include/zirvtk.h) allows C/C++ compositors to create and manage widgets through a stable ABI.

Full documentation on the ZirvTK page.

26. ZirvUI Compositor

User-space graphical compositor connecting to DisplayJet via ZirvFlux. Freestanding ELF64 binary. Renders procedural background gradient, 28-pixel top panel with hamburger menu and "ZirvUI" branding, system tray (WiFi, Bluetooth, speaker, battery, user, power icons), and live uptime clock in 5x7 bitmap font.

Full documentation on the ZirvUI page.

27. Creating a MOSIX Distribution

A MOSIX distribution is any operating system that implements the MOSIX standard. To create one:

  1. Choose or build a kernel: Use Zirvium as-is, fork it, or write your own from scratch implementing the MOSIX syscall ABI
  2. Provide a C library: Use zirvlibc or implement the MOSIX syscall wrappers yourself
  3. Implement the filesystem: Create the MOSIX hierarchy (/bin, /lib, /user, /boot, /config, /zirv, /mounts, /tmp)
  4. Provide a console: At minimum, a /zirv/tty/virtual0 device for shell I/O
  5. Add userspace: Use zirvinit, zirvshell, and zirvutils, or write your own
  6. Add drivers: Port existing Zirvium drivers or write new ones following the driver framework

See the Distributions page for a full guide.
